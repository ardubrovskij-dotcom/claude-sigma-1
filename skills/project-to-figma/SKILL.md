# Проект → Figma

Задача навыка — чтобы макет выглядел так, будто его делал дизайнер этого проекта: в его цветах, шрифтах и тоне, про его содержание. Рисование — последний шаг; основная ценность в том, чтобы правильно прочитать контекст и спланировать.

Порядок: **связь → контекст → стиль → задача → бриф → «ок» → отрисовка → проверка → отчёт.**

## 0. Связь с Figma

Вызови `figma_status`.
- `connected: true` — запомни файл и страницы, продолжай.
- Плагин не подключён — попроси пользователя открыть в Figma Desktop **Plugins → Development → Claude for Figma by Dubrovskiy** и нажать **Подключить**. Контекст и бриф можно готовить параллельно, рисовать — только после подключения.
- Инструментов `figma_*` нет совсем — сначала пойми, где идёт сессия:
  - **Claude Desktop (чат)** — расширение выключено: **Settings → Extensions → Claude for Figma by Dubrovskiy → Enabled**.
  - **Claude Code на компьютере пользователя** — мост не подключён к Claude Code: запустить `bridge/install-claude-code.command` из репозитория claude-sigma (один раз, для всех репозиториев) и перезапустить сессию.
  - **Облачная сессия** (контейнер, репозиторий клонирован на сервер) — напрямую до Figma на компьютере она не дотянется; работает через облачный ретранслятор. Если `figma_status` отвечает `bridge: "relay"` — всё настроено, просто попроси включить в плагине блок «Облако». Если инструментов нет — окружение не настроено: предложи (а) настроить один раз по разделу «Облако» в README репозитория claude-sigma (ретранслятор Cloudflare + переменная `SIGMA_RELAY_URL` + Setup script); (б) открыть репозиторий в локальной сессии; (в) режим экспорта — см. ниже.

### Режим экспорта (когда Figma недоступна)

Всё до брифа включительно делается как обычно. После «ок» вместо отрисовки сохрани каждый фрейм в файл `figma-export/<NN>-<имя>.json` — массив команд для одного фрейма (тот же формат, что `commands` у `figma_batch`, ссылки `"$N"` внутри файла). Пользователь открывает плагин в Figma, вставляет содержимое файла в «Ручная команда» и нажимает «Выполнить» — массив выполнится как пакет. Скриншотов для проверки в этом режиме нет: проверь пакеты особенно тщательно по `references/commands.md` и попроси пользователя прислать скриншот результата.

## 1. Контекст проекта

Собери всё, что говорит о содержании и стиле. Источники по убыванию надёжности:

| # | Источник | Что искать |
|---|---|---|
| 1 | Слова пользователя в этом чате | Явные указания по стилю, цветам, шрифтам, тексту — они важнее всего остального |
| 2 | Инструкции проекта | Тон, аудитория, бренд, запреты |
| 3 | Файлы знаний проекта и вложения | Брендбук, гайдлайны, презентации, тексты, CSS/Tailwind/токены, логотипы, скриншоты |
| 4 | Текущий файл Figma | Уже нарисованные фреймы: их палитра, шрифты, сетка — продолжать, а не спорить с ними |
| 5 | Тематика и аудитория проекта | Если стиля нигде нет — вывести его из предмета (финтех ≠ детское приложение) |

Как читать:
- Если есть поиск по знаниям проекта — ищи по словам «бренд», «brand», «цвет», «color», «шрифт», «font», «логотип», «гайдлайн», «tone of voice», названию продукта.
- Картинки (скриншоты, логотипы) рассматривай сам: цвета с изображения — приблизительные, помечай их «≈».
- Существующий макет: `figma_command get_page {depth: 1}` → `figma_screenshot` 1–2 характерных фреймов → `get_node {depth: 2}` по ним, чтобы взять точные hex и шрифты.

Подробно о том, как вытаскивать токены из каждого вида источника, — `references/style-extraction.md`.

Если контекста нет вообще (пустой проект, нет вложений) — не выдумывай «бренд». Скажи, что стиль будет предложен с нуля, и предложи его в брифе.

## 2. Стиль → токены

Сведи найденное в короткую систему токенов. Это нужно, чтобы все фреймы были согласованы и правки делались в одном месте плана, а не в каждом слое.

- **Цвета по ролям**: `bg`, `surface`, `text`, `text-muted`, `primary`, `accent`, + `success/warning/danger` для UI. Один ведущий цвет, остальные — поддержка.
- **Шрифты**: заголовочный и текстовый + начертания. Сразу проверь `figma_command list_fonts {family}`: названия начертаний зависят от установки («Semi Bold» ≠ «SemiBold»). Нет шрифта бренда — возьми близкий доступный и скажи об этом в брифе.
- **Шкала размеров** под формат (`references/formats.md`), отступы кратные 4/8, радиусы, тени.
- **Тон**: строгий / дружелюбный / премиальный / технический — влияет на плотность, радиусы, контраст.

Каждый токен помечай источником: `[бренд]`, `[макет]`, `[вложение ≈]`, `[предложено]`. Пользователь сразу видит, что взято из проекта, а что придумано.

Проверь контраст: основной текст к фону ≥ 4.5:1, крупные заголовки ≥ 3:1 (формула — в `references/style-extraction.md`). Если брендовая пара не проходит — оставь цвет бренда для акцентов, а текст сделай темнее/светлее.

## 3. Задача → формат

Определи тип результата — от него зависят размеры, сетка и приёмы:

| Тип | Признаки в запросе | Справка |
|---|---|---|
| Презентация | «презентация», «слайды», «питч», «колода», «доклад» | `references/formats.md#презентации` |
| Экран / UI | «экран», «страница», «лендинг», «интерфейс», «дашборд» | `references/formats.md#экраны` |
| Прототип | «прототип», «флоу», «сценарий», «user flow», несколько экранов | `references/formats.md#прототипы` |
| Фреймворк / схема | «матрица», «воронка», «процесс», «схема», «оргструктура», «roadmap» | `references/formats.md#схемы` |
| Соцсети / баннер | «пост», «сторис», «обложка», «баннер» | `references/formats.md#соцсети` |

Содержание бери из проекта: реальные названия, цифры, тезисы, пункты меню. Плейсхолдеры («Lorem ipsum», «Заголовок») — только там, где данных правда нет, и с пометкой в брифе. Слайд — одна мысль; если материала много, план растёт по числу слайдов, а не по плотности.

## 4. Бриф и подтверждение

Перед отрисовкой покажи бриф **в этом виде** и жди ответа. Это одна дешёвая остановка вместо перерисовки десяти фреймов.

```
## Бриф: <что рисуем>

**Источники:** <что прочитано: файлы, инструкции, макет; чего не нашлось>
**Формат:** <тип>, <размер>, <кол-во фреймов>, страница «<имя>»

**Стиль**
| Роль | Значение | Источник |
|---|---|---|
| bg | #0B1220 | [бренд] |
| primary | #3B82F6 | [макет] |
| заголовки | Manrope Bold 96 | [предложено: шрифта бренда нет] |
| текст | Inter Regular 28 | [бренд] |
Тон: <одна фраза>. Мотив: <повторяющийся элемент>.

**План**
1. <Фрейм 1> — <что на нём, какая раскладка>
2. <Фрейм 2> — …

**Допущения / вопросы:** <что предположено; 0–3 вопроса>

Рисую по этому плану? Можно поправить любой пункт.
```

Когда бриф можно пропустить: правка одного существующего элемента («сделай заголовок крупнее», «поменяй цвет кнопки») или пользователь прямо сказал «без брифа, сразу рисуй». Тогда кратко скажи, что меняешь, и делай.

На ответ «ок / да / рисуй» — рисуй. На правки — обнови бриф (коротко, только изменения) и снова спроси, если правки существенные; мелкие — просто учти.

## 5. Отрисовка

Справочник команд и правила API — `references/commands.md`. Готовые заготовки пакетов — `references/recipes.md`. Прочитай их перед первым `figma_batch` в разговоре.

Порядок:
1. **Страница.** Для нового набора — `create_page {name: "<Тема> — <дата>"}`, чтобы не смешивать с чужими макетами. Дорисовка к существующему — на текущей странице.
2. **Один `figma_batch` на фрейм.** Слайд, экран или схема — целиком одним пакетом: фрейм первым, дети с `parentId: "$0"`. Между фреймами — отдельные пакеты, так ошибка в одном не ломает остальные.
3. **Позиции.** Фреймы верхнего уровня без `x/y` плагин сам ставит в ряд правее существующих — не задавай им координаты, если не нужен особый порядок.
4. **Имена слоёв.** Фреймы: `01 — Титул`, `02 — Проблема`; экраны: `Home`, `Home / Empty`; внутри — по смыслу (`Title`, `CTA`, `Card / Pricing`). Дизайнер, открывший файл, должен понимать структуру.
5. **Токены, а не импровизация.** Используй ровно значения из брифа. Новый цвет посреди работы — признак, что токены неполны: дополни их и скажи об этом в отчёте.
6. **Auto layout для UI.** Кнопки, карточки, списки, навбары — контейнеры с `layoutMode`; текст в них с `layoutSizingHorizontal: "FILL"` или `width`. Так макет переживает правку текста.
7. **Иконки и логотипы** — только `create_svg`. Растровые изображения плагин не вставляет: ставь прямоугольник-заглушку `surface` с подписью «Фото: <что>» и скажи об этом.
8. **Ошибка пакета** (`error.index`): команды до неё уже выполнены. Не перезапускай пакет целиком — исправь причину и продолжи с упавшей команды, либо удали созданное (`delete_node {ids}`) и повтори.

## 6. Проверка

После каждого фрейма (для колоды — после каждых 2–3) — `figma_screenshot {id, scale: 0.5}` и посмотри критично:

- текст не вылезает за фрейм и не обрезан, нет «столбиков» из одного слова;
- ничего не наезжает друг на друга без умысла;
- иерархия читается с первого взгляда: заголовок — самое заметное;
- контраст текста достаточный;
- соответствие брифу: цвета, шрифты, план.

Нашёл проблему — исправь `update_node` по id и сделай снимок ещё раз. Один цикл исправления на фрейм обычно достаточен; не делай повторных снимков без изменений.

## 7. Отчёт

Коротко, в этом порядке:
1. Что нарисовано: страница, список фреймов с id.
2. Что отклонилось от брифа и почему (замена шрифта, заглушки картинок, разбитый на два слайд).
3. Что можно сделать следующим шагом (1–3 предложения).

## Правки после отрисовки

Пользователь просит поменять нарисованное — сначала `get_node {id, depth: 2}` (или `find_nodes`), чтобы работать по настоящим id, затем `update_node`. Перерисовывать фрейм целиком — только если меняется раскладка. Стилевые правки («сделай всё темнее») применяй ко всем фреймам набора, а не к одному: согласованность важнее.

## Ограничения плагина (говори о них честно)

| Нельзя сейчас | Что делать |
|---|---|
| Вставить растровое фото | Заглушка с подписью |
| Связать экраны интерактивными переходами (prototype links) | Стрелки-связи на схеме флоу + список переходов в отчёте |
| Создать переменные/стили Figma | Токены применяются как значения; список токенов — в отчёте |
| Работать с закрытым плагином | Попросить открыть плагин и нажать «Подключить» |
